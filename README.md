# Volume Mixer 2.0

Arduino-controlled per-app audio mixer. A Nano with 4 knobs + an analog
joystick reports state over serial; this Tauri app maps knobs to per-app
Windows volume (via Core Audio) and renders a click-through HUD overlay for
navigating banks/channels without touching the mouse.

## Project layout

- `arduino/mixer_firmware.ino` — reference copy of the flashed firmware (docs only, not built by this project)
- `src-tauri/` — Rust backend
  - `src/serial.rs` — serial read loop, protocol parsing, joystick debounce/axis-lock/repeat, button click/double-click/mute-timer logic
  - `src/audio/` — `AudioBackend` trait + the Windows Core Audio (WASAPI) implementation
  - `src/config.rs` — persisted config (last COM port, per-channel app assignment + colors)
  - `src/state.rs` — shared runtime state, the `overlay-state` event payload
  - `src/window.rs` — overlay click-through toggle + top-center positioning
  - `src/tray.rs` — system tray (Show / Quit)
- `dist/overlay/` — the HUD window (borderless, transparent, always-on-top, click-through while collapsed)
- `dist/main/` — the settings window (COM port picker, live assignment overview)

## Prerequisites

1. **Rust** (stable) — https://rustup.rs. This machine did not have `cargo`/`rustc` on PATH when this project was scaffolded — install it before running anything below.
2. **Node.js** (already present) and npm.
3. **Tauri v2 system dependencies for Windows** — the WebView2 runtime (preinstalled on most Windows 10/11 machines) and the standard MSVC build tools (Visual Studio Build Tools with the "Desktop development with C++" workload). See https://v2.tauri.app/start/prerequisites/.
4. Install JS deps once: `npm install`.

## Development

```bash
npm run dev
```

This runs `tauri dev`, which compiles the Rust backend and opens both windows (main + overlay) with hot-reload on frontend file changes. First compile will be slow (pulling in the `windows` crate + Tauri); subsequent ones are incremental.

## Building an installer

```bash
npm run build
```

Produces an NSIS installer under `src-tauri/target/release/bundle/nsis/`.

## First run

1. Plug in the Nano.
2. Launch the app (`npm run dev` or the built installer). The main window opens automatically on first run.
3. The app tries to auto-connect to whatever COM port was used last (persisted in the app's config file). On first run there's nothing saved yet, so:
   - Open the main window (tray icon → Show, if it's hidden).
   - Under **Serial connection**, hit **Refresh**, pick the Nano's port, and click **Connect**. It's remembered for next launch.
4. The overlay HUD appears top-center of the screen as a small `BANK 1` pill. Click the joystick to expand it.
5. While expanded, click a channel's name to assign it to a running app's audio session (only apps currently producing audio show up), or the gear icon to set a per-channel background/selection color.
6. Navigate with the joystick (↑↓ bank, ←→ channel), click to mute the selected channel, double-click to collapse. Knobs 1–4 always control the volume of whichever 4 channels belong to the active bank.

## Known limitations (by design, not bugs)

- Only works over borderless/windowed-fullscreen games. True exclusive fullscreen bypasses the desktop compositor — nothing can render above it without hooking the game's own graphics API.
- Per-app volume control is Windows-only for now (`AudioBackend` trait in `src-tauri/src/audio/mod.rs` is structured so a macOS/Linux backend can be added later without touching the rest of the app).
- Channel icons are a placeholder (first letter of the app name) — real per-exe icon extraction wasn't in scope for v1.
- If two assignable sessions share the same exe name (e.g. multiple windows of the same app), they're treated as one channel-assignable id — Windows' per-session audio API doesn't give a stable app identity, only per-*session*, so this is a reasonable v1 simplification and matches how most volume mixers dedupe by app anyway.

## Flagged assumptions — please confirm

The spec didn't cover these; I made a specific call so the app has *some*
consistent behavior, but you should sanity-check them:

1. **Diagonal joystick priority.** The firmware only reports discrete
   direction labels (`RIGHT`/`LEFT`/`NEUTRAL`, `UP`/`DOWN`/`NEUTRAL`), not
   raw magnitudes — so if both axes cross their threshold in the same tick
   (a true diagonal push), there's no way to tell which one "wins" by
   distance like the mockup's mouse-drag version could. I made X (channel
   navigation) take priority over Y (bank navigation) when both are
   simultaneously non-neutral and no axis is currently locked. This is in
   `src-tauri/src/serial.rs::step_nav`.
2. **Axis "release" threshold.** The mockup used a smaller release
   threshold than fire threshold (hysteresis) to avoid jitter right at the
   boundary. The firmware only gives us the already-thresholded label, so
   there's just one boundary — axis lock releases when that axis's label
   returns to `NEUTRAL`. Functionally close to the mockup's intent, but not
   identical.
3. **Selected channel index persists across bank switches** (not reset to
   0), matching the mockup's `state.channel` being a single global value
   rather than per-bank.
